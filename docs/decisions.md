# บันทึกการตัดสินใจ

เอกสารนี้บันทึกว่า**ทำไมระบบถึงเป็นแบบนี้** พร้อมตัวเลขที่ใช้ตัดสินใจ
เพื่อไม่ให้ใครต้องมาไล่หาเหตุผลใหม่ หรือรื้อของที่ตั้งใจทำไว้แล้วโดยไม่รู้

แต่ละข้อเขียนเป็น: บริบท → สิ่งที่เลือก → หลักฐาน → ผลที่ตามมา

---

## 1. ใช้ TF-IDF + Naive Bayes ทั้งที่ Linear SVM แม่นกว่า

**บริบท** เอกสารบทที่ 3.3.3 กำหนดให้เปรียบเทียบ 5 อัลกอริทึม × 6 ตัวชี้วัด
ตอนข้อมูลมี 95 แถว ทุกอัลกอริทึมได้ accuracy `1.0` เท่ากันหมดจนเลือกไม่ได้
พอมีข้อมูลจริง 39,320 แถว ความต่างจึงปรากฏ

**หลักฐาน** (ชุดทดสอบภาษาอังกฤษ 9,831 ฉบับ)

| อัลกอริทึม | accuracy | recall | เวลาเทรน | เวลาทำนาย |
|---|---:|---:|---:|---:|
| SVM (LinearSVC) | 0.9790 | 0.9797 | 7.40 s | 0.0023 s |
| RandomForest | 0.9706 | 0.9581 | 11.92 s | 0.1426 s |
| LogisticRegression | 0.9685 | 0.9688 | 0.19 s | 0.0019 s |
| **NaiveBayes (ที่ใช้)** | 0.9109* | 0.8490* | 0.014 s | 0.0035 s |
| KNN | 0.8690 | 0.8644 | 0.011 s | 13.15 s |

\* ค่าก่อนปรับพารามิเตอร์ หลังปรับแล้วได้ **0.9687** (ดูข้อ 2)

ตารางนี้วัดตอนที่ `evaluate.py` ยังใช้ `min_df=1` ไม่ตรงกับ `train.py` (แก้แล้ว ดูข้อ 11)
ตัวเลขล่าสุดอยู่ใน `ml/results/algorithm_comparison_en.csv` ลำดับยังเหมือนเดิม
SVM 0.9832 และ NaiveBayes 0.9679 ซึ่งตรงกับโมเดลจริงแล้ว

**สิ่งที่เลือก** คง Naive Bayes ไว้

**เหตุผล** เอกสารบทที่ 3 เขียนอิงอัลกอริทึมนี้ไว้แล้วทั้งแผนภาพคลาส `PhishingModel`
และพจนานุกรมข้อมูล การเปลี่ยนจะทำให้เอกสารไม่ตรงกับระบบ

นอกจากนี้ Naive Bayes **ตีความได้ว่าคำไหนทำให้เสี่ยง** ผ่าน `feature_log_prob_`
ซึ่งระบบใช้ไฮไลต์คำเสี่ยงให้ผู้ใช้เห็น — เป็นความสามารถที่ LinearSVC ให้ไม่ได้ตรง ๆ
และเป็นหัวใจของ UC-06

**ผลที่ตามมา** ตารางเปรียบเทียบยังต้องรายงานตามจริงว่า SVM ได้คะแนนสูงกว่า
แล้วอธิบายว่าเลือก Naive Bayes ด้วยเหตุผลอื่น ซึ่งเป็นการเขียนงานวิจัยที่น่าเชื่อถือกว่า
การเลือกโดยไม่เปรียบเทียบ

## 2. ปรับพารามิเตอร์แทนการเปลี่ยนอัลกอริทึม

**บริบท** เมื่อคง Naive Bayes ไว้ ต้องหาความแม่นยำจากที่อื่น

**หลักฐาน** ทดลอง 9 ชุดบนข้อมูลจริง

| max_features | min_df | alpha | accuracy | คลังคำ |
|---:|---:|---:|---:|---:|
| **20,000** (ค่าเดิม) | 1 | 0.1 | 0.9027 | 20,000 |
| 50,000 | 1 | 0.1 | 0.9287 | 50,000 |
| 100,000 | 1 | 0.1 | 0.9453 | 100,000 |
| ไม่จำกัด | 1 | 0.1 | 0.9651 | 2,104,501 |
| ไม่จำกัด | 1 | 0.05 | **0.9702** | 2,104,501 |
| **ไม่จำกัด** | **2** | **0.05** | **0.9686** | **668,481** |
| ไม่จำกัด (unigram) | 1 | 0.1 | 0.9343 | 233,475 |

**สิ่งที่เลือก** `max_features=None`, `min_df=2`, `alpha=0.05`

**เหตุผล** เพดาน `max_features = 20000` ถูกตั้งไว้ตอนข้อมูลมี 95 แถว
ซึ่งตอนนั้นไม่เคยถูกแตะเลย พอข้อมูลโตขึ้น 400 เท่ามันกลายเป็นคอขวดหลักทันที

ไม่เลือกตัวที่ accuracy สูงสุด (`min_df=1`) เพราะ **แลกไม่คุ้ม**

| | ไม่จำกัด | min_df=2 |
|---|---|---|
| accuracy | 0.9702 | 0.9686 (−0.0016) |
| ไฟล์โมเดล | 129 MB | **40 MB** |
| เวลาทำนาย/ฉบับ | 12.67 ms | **4.39 ms** |

ไฟล์ 129 MB ต้องเข้า Docker image และโหลดขึ้นหน่วยความจำทุกครั้งที่ container เริ่ม
แลกกับ accuracy ที่เพิ่มแค่ 0.16% ไม่คุ้ม

`min_df` ปรับตามขนาดข้อมูลอัตโนมัติ (`MIN_DOCS_FOR_MIN_DF = 1000`) เพราะถ้าใช้ 2
กับภาษาไทยที่มี 137 แถว คำส่วนใหญ่โผล่ครั้งเดียวจะถูกตัดจนคลังคำแทบหมด

**ผล** accuracy 5-fold CV **0.9092 → 0.9687** และฟิชชิงหลุดรอด **15.1% → 5.1%**

## 3. รายงานผลด้วย k-fold cross-validation ไม่ใช่การแบ่งครั้งเดียว

**บริบท** เดิมแบ่ง 80/20 ครั้งเดียวด้วย `random_state=42`

**หลักฐาน** บนข้อมูลสังเคราะห์ 143 แถว การแบ่งครั้งเดียวให้ accuracy `1.0000`
แต่ 5-fold CV ให้ **0.9497 ± 0.0273** — ค่า `1.0000` เป็นเพียงโชคของการแบ่ง

**สิ่งที่เลือก** `train.py` รายงานทั้งสองค่าควบคู่กัน และสร้าง TF-IDF ใหม่ทุก fold
ผ่าน `Pipeline` เพื่อไม่ให้คำจากชุดตรวจรั่วเข้าคลังคำตอนเทรน

**ผลที่ตามมา** ค่าที่ควรนำไปรายงานในบทที่ 3.4 คือค่า CV พร้อมส่วนเบี่ยงเบนมาตรฐาน
ซึ่งตอนนี้แคบมาก (`± 0.0015`) เพราะข้อมูลเพียงพอแล้ว

## 4. ข้อความที่โมเดลไม่รู้จักต้องไม่ถูกตัดสินว่าอันตราย

**บริบท** เมื่อไม่มีคำใดในอีเมลอยู่ในคลังคำ เวกเตอร์ TF-IDF จะว่างเปล่า
`predict_proba` จึงคืนเพียงค่า prior ของคลาส

**หลักฐาน** ก่อนแก้ ข้อความสามแบบที่ต่างกันสิ้นเชิงได้ผลเท่ากันเป๊ะ

```
ตัวเลขล้วน        -> 55.79%  dangerous
คำที่ไม่มีความหมาย  -> 55.79%  dangerous
ภาษาที่ไม่รองรับ    -> 55.79%  dangerous
```

55.79% สูงกว่าเกณฑ์อันตราย 50% ผลคืออีเมลปกติที่ใช้คำนอกคลังคำถูกเตือนว่าอันตราย

**สิ่งที่เลือก** ถ้าไม่มีภาษาใดมีคำที่รู้จักเลย ให้รายงาน `0.0` พร้อมตัวชี้วัด
`no_known_terms` อธิบายให้ผู้ใช้ทราบว่าผลนี้ไม่ได้มาจากการวิเคราะห์เนื้อหา

**เหตุผล** ระบบมีหน้าที่ชี้ว่า "พบสัญญาณฟิชชิง" การไม่พบสัญญาณใดเลยไม่ใช่หลักฐานว่าอันตราย
และการเตือนผิดบ่อย ๆ จะทำให้ผู้ใช้เลิกสนใจคำเตือนทั้งหมด

## 5. ค่าเริ่มต้นไม่เก็บข้อมูลส่วนบุคคล

**บริบท** เดิม `STORE_EMAIL_CONTENT=true` และเก็บคำรายอีเมลเสมอ

**หลักฐาน** `tokenized_word.word` เก็บคำเป็นข้อความธรรมดาผูกกับ `email_id` เดียวกับ
`body_encrypted` ทำให้คำสั่งเดียวประกอบเนื้อหาอีเมลกลับได้โดยไม่ต้องใช้กุญแจ

```sql
SELECT word FROM tokenized_word WHERE email_id = '...'
```

**สิ่งที่เลือก** `STORE_EMAIL_CONTENT=false` และเพิ่ม `STORE_NLP_ARTIFACTS=false`
พร้อมลบข้อมูลอัตโนมัติเมื่อครบ `DATA_RETENTION_DAYS` (90 วัน)

**ผลที่ตามมา** การเก็บข้อมูลเพื่อทำวิจัยบทที่ 4 ต้องเปิด `STORE_NLP_ARTIFACTS=true`
เอง และต้องแจ้งผู้ใช้ — ซึ่งเป็นสิ่งที่ควรทำอยู่แล้ว

เปลี่ยน `body_hash` จาก SHA-256 เป็น HMAC ที่มีกุญแจด้วย เพราะ SHA-256 ธรรมดา
ทำให้ผู้ที่มีสำเนาอีเมลอยู่แล้วแฮชมาเทียบได้ว่าเป้าหมายเคยเปิดอ่านอีเมลฉบับนั้นหรือไม่

**เหตุผล** เสิร์ฟจาก origin เดียวกันทำให้ไม่ต้องตั้งค่าที่อยู่เซิร์ฟเวอร์และไม่ติด CORS

## 8. ประกาศโปรเจคเป็นแพ็กเกจด้วย pyproject.toml

**บริบท** มี `sys.path.insert()` เขียนด้วยมืออยู่ 6 จุด เพื่อให้ `import common` และ
`import app` ทำงานได้

**ปัญหา** ย้ายไฟล์ทีต้องนับ `parents[N]` ใหม่ ต้องจำว่าคำสั่งไหนต้อง `cd` ไปไหนก่อน
และ IDE กับ linter มองไม่เห็น import จึงฟ้องผิดตลอด

**สิ่งที่เลือก** `pyproject.toml` ตาม PEP 621 ประกาศ `common` และ `app` เป็นแพ็กเกจ
ติดตั้งด้วย `pip install -e ".[ml,dev]"`

**ผลที่ตามมา** `sys.path` หายหมดทั้ง 6 จุด และ `import app.main` จาก repo root
ทำได้แล้ว ซึ่งเดิมทำไม่ได้เลย

รวมรายการ dependencies ไว้ที่เดียวด้วย เดิมกระจาย 3 ไฟล์และมี `scikit-learn==1.5.0`
ซ้ำกันสองที่ ซึ่งเสี่ยงมากเพราะ**เวอร์ชัน sklearn ต้องตรงกัน ไม่งั้นโหลดไฟล์โมเดลที่เทรนไว้ไม่ได้**

## 9. ชุดข้อมูลที่ใช้และข้อจำกัดในการตีความ

| ชุด | จำนวน | หมายเหตุ |
|---|---:|---|
| `mock_email_dataset.xlsx` | ~230 | ชุดจำลองเดิมของโครงงาน |
| `synthetic_email_dataset.csv` | 274 | เขียนขึ้นเองเพื่อขยายคลังคำ ไม่ใช่อีเมลจริง (เพิ่มภาษาไทย 154 ฉบับ ดูด้านล่าง) |
| `CEAS_08.csv` | 39,154 | ชุดสาธารณะ ภาษาอังกฤษ |
| `spam_and_ham_classification.csv` | 9,989 | ชุดสาธารณะ ภาษาอังกฤษ |
| `tu_scam_dataset.csv.xlsx` | 2,999 | ข้อความหลอกลวงภาษาไทยสังเคราะห์ ตัด `suspicious` 754 แถวทิ้งเหลือ 2,245 |

หลังรวมและกรองแล้ว อังกฤษ **49,214 ฉบับ** ไทย **2,508 ฉบับ** (ตัดภาษาอื่นออก 170 ฉบับ)
ข้อความจาก `tu_scam_dataset` ที่เป็นอังกฤษล้วน 63 ฉบับไปอยู่ฝั่งอังกฤษ

**ข้อจำกัดที่ต้องเขียนกำกับตอนรายงานผล**

1. ชุดสาธารณะทั้งสองเป็น**ภาษาอังกฤษล้วน** และข้อมูลไทยทั้งหมดเป็นข้อมูลสังเคราะห์
   ยังไม่มีอีเมลไทยจริงเลย
2. `spam_and_ham_classification.csv` ติดป้ายว่า **spam** ซึ่งกว้างกว่า **phishing**
   เพราะรวมโฆษณาที่ไม่ได้หลอกเอาข้อมูล โมเดลจึงเรียนรู้ "อีเมลไม่พึงประสงค์"
   มากกว่า "อีเมลหลอกเอาข้อมูล" โดยเคร่งครัด
3. ข้อมูลสังเคราะห์มีรูปแบบสม่ำเสมอกว่าอีเมลจริงมาก
   ใช้ขยายคลังคำได้ แต่ไม่ควรนับรวมตอนอ้างว่าทดสอบกับข้อมูลจริง
4. **CV ภาษาไทย 0.9936 สูงเกินจริง** `tu_scam_dataset` สร้างจากแม่แบบที่ต่างกันแค่ emoji
   หรือช่องว่าง (คลังคำภาษาไทยทั้งหมดมีแค่ราว 2,400 คำ ข้อความยาวเฉลี่ย 11 คำ)
   การสุ่มแบ่ง 80/20 จึงได้ข้อสอบที่หน้าตาแทบเหมือนข้อที่เทรน ต้องรายงานคู่กับผลทดสอบข้ามแหล่งด้านล่าง

### ทดสอบข้ามแหล่ง (ภาษาไทย)

กันข้อมูลไว้ทีละแหล่ง เทรนด้วยแหล่งที่เหลือ แล้วทดสอบกับแหล่งที่กันไว้ซึ่งโมเดลไม่เคยเห็นรูปแบบเลย
ใกล้เคียงสถานการณ์ใช้งานจริงกว่า CV (ผลอยู่ที่ `ml/results/cross_source_th.csv`)

| แหล่งที่ใช้ทดสอบ | จำนวน | accuracy | precision | recall |
|---|---:|---:|---:|---:|
| `tu_scam_dataset` | 2,182 | 0.8607 | 0.8430 | 0.8778 |
| ชุดเดิม (mock + synthetic) | 172 | 0.9535 | 0.9667 | 0.9457 |
| เขียนเพิ่ม 154 ฉบับ | 154 | 0.8442 | 0.7872 | 0.9487 |

**ความหลากหลายของแหล่งช่วยได้จริง** ตอนมีแค่สองแหล่ง เทรนด้วย `tu_scam_dataset`
แล้วทดสอบกับชุดเดิมได้แค่ **0.6802** เพิ่มแหล่งที่สามแล้วขึ้นเป็น 0.9535

ข้อมูลที่เขียนเพิ่ม 154 ฉบับเน้นกรณีที่แยกยาก คืออีเมลปกติที่มีคำว่า OTP บัญชี ลิงก์ หรือโอนเงิน
(เช่นการแจ้งเตือนจริงจากธนาคาร) กับฟิชชิงที่เขียนสุภาพไม่เร่งเร้า
ก่อนนำเข้า โมเดลที่เทรนด้วยสองแหล่งแรกทำได้ 0.8312 บนชุดนี้
โดยพลาดเพราะตัดสินอีเมลปกติเป็นฟิชชิง 21 จาก 76 ฉบับ precision 0.7872 ในตารางบอกว่าปัญหานี้ยังเหลืออยู่

## 10. นับข้อความไทยปนอังกฤษเป็นภาษาไทย

**บริบท** `detect_language()` เดิมเลือกภาษาที่มีตัวอักษรมากกว่า
ข้อความอย่าง "ระบบ TU แจ้งเตือน ให้ update password ผ่าน bit.ly/... ด่วน" มีอักษรละตินมากกว่า
เพราะคำอังกฤษยาวกว่า จึงถูกส่งไปเทรนโมเดลอังกฤษ พบ 125 ฉบับใน `tu_scam_dataset`

**หลักฐาน** ชุดข้อมูลอังกฤษ 49,000 ฉบับ**ไม่มีอักษรไทยปนเลยสักฉบับ**
แต่คนไทยเขียนไทยปนอังกฤษเป็นปกติ

**สิ่งที่เลือก** นับเป็นไทยเมื่อมีอักษรไทยอย่างน้อย 15% (`THAI_RATIO_THRESHOLD`)
ใช้ค่าเดียวกับ `min_language_ratio` ของ backend ซึ่งเป็นเกณฑ์ที่ backend ใช้ตัดสินว่าจะส่งข้อความให้โมเดลไทย
โมเดลไทยจึงเทรนด้วยข้อความแบบเดียวกับที่จะได้รับจริง

**ผลกระทบ** ใช้แค่ตอน preprocess backend ใช้ `script_ratios()` โดยตรง จึงไม่กระทบระบบที่รันอยู่

## 11. ตารางเปรียบเทียบอัลกอริทึมต้องใช้ vectorizer แบบเดียวกับโมเดลจริง

**บริบท** `evaluate.py` เรียก `build_vectorizer()` โดยไม่ส่งจำนวนเอกสาร จึงได้ `min_df=1`
ขณะที่ `train.py` ได้ `min_df=2`

**หลักฐาน** บนข้อมูลชุดเดียวกัน Naive Bayes ในตารางได้ **0.9109** แต่โมเดลจริงได้ **0.9687**
ต่างกันเกือบ 6 จุด ไม่ใช่แค่ "ไม่ตรงเป๊ะ" อย่างที่เคยเข้าใจ

**สิ่งที่เลือก** ส่งจำนวนแถวเข้าไปเหมือน `train.py` ตอนนี้แถว NaiveBayes ในตาราง
ตรงกับ `model_metadata.json` ทุกตัวเลข ถ้าบทที่ 3.3.3 อ้างตัวเลขจากตารางเดิมต้องแก้ตาม

## 12. ระบบบัญชีผู้ใช้ออกแบบให้เก็บข้อมูลน้อยที่สุด

**บริบท** หน้า `/login` เดิมเป็นแบบร่าง ผู้ใช้ขอให้มีระบบสมัครสมาชิกที่บันทึกลงตารางจริง
และคำนึงถึงความเป็นส่วนตัว การตรวจอีเมลยังต้องใช้ได้โดยไม่ต้องมีบัญชีเหมือนเดิม

**สิ่งที่เลือก**

| เรื่อง | ทำแบบนี้ | เหตุผล |
|---|---|---|
| ข้อมูลที่ขอ | อีเมล + รหัสผ่านเท่านั้น | ไม่มีฟีเจอร์ใดต้องใช้ชื่อหรือเบอร์โทร |
| อีเมล | HMAC ไว้ค้นหา + Fernet ไว้แสดงผล | ฐานข้อมูลรั่วก็ไม่ได้รายชื่ออีเมล |
| รหัสผ่าน | scrypt (N=2^14) จาก `hashlib` | ไม่ต้องเพิ่ม dependency และทนการเดาด้วย GPU |
| การเข้าสู่ระบบ | token สุ่ม เก็บแค่ SHA-256 ในตาราง `user_session` | ยกเลิกที่เซิร์ฟเวอร์ได้จริงตอนออกจากระบบ ต่างจาก JWT ที่ใช้ได้จนหมดอายุ |
| อายุ | 12 ชั่วโมง หรือ 30 วันเมื่อเลือกจดจำ | ลดความเสี่ยงเมื่อลืมออกจากระบบบนเครื่องสาธารณะ |
| ความยินยอม | ต้องติ๊กเอง บันทึกฉบับของนโยบาย + เวลา | ยืนยันได้ว่าแต่ละคนยินยอมกับเนื้อหาฉบับไหน |
| ผลการตรวจอีเมล | ไม่ผูกกับบัญชี | ถ้าผูก ผู้อ่านฐานข้อมูลจะรู้ว่าใครได้รับอีเมลแบบไหน |
| สิทธิ์ของเจ้าของ | ดูข้อมูลทั้งหมดและลบบัญชีได้เอง | ไม่ต้องติดต่อผู้ดูแล |
| login ผิด | ข้อความเดียวกันและใช้เวลาเท่ากัน ทั้งอีเมลไม่มีและรหัสผิด | ไม่ให้ใช้หน้านี้ไล่เช็คว่าใครมีบัญชี |

**หลักฐาน** เทสต์ใน `backend/tests/test_auth.py` ตรวจว่าในฐานข้อมูลไม่มีอีเมล รหัสผ่าน หรือ token
เป็นข้อความธรรมดา และลบบัญชีแล้วไม่เหลือแถวใดในทั้งสองตาราง
ทดสอบผ่านหน้าเว็บจริงด้วย Chrome แบบ headless ครบทุกขั้น ตั้งแต่สมัคร เข้าสู่ระบบ ออกจากระบบ ไปจนถึงลบบัญชี
และตรวจว่า log บันทึกแค่ `user_id` ไม่มีอีเมล

**ข้อจำกัดที่ยอมรับ**
- ไม่มีการยืนยันอีเมลและลืมรหัสผ่าน เพราะระบบยังส่งอีเมลไม่ได้ จึงสมัครด้วยอีเมลของคนอื่นได้
- หน้าสมัครตอบ 409 เมื่ออีเมลซ้ำ จึงยังบอกได้ว่าอีเมลใดมีบัญชี ถ้าไม่บอก ผู้ใช้จริงจะไม่รู้ว่าทำไมสมัครไม่ได้
  ความเสี่ยงที่เหลือจำกัดด้วย rate limit 10 ครั้งต่อนาที
- ถ้าเปลี่ยน `ENCRYPTION_KEY` จะถอดอีเมลเดิมไม่ได้ แต่ยังเข้าสู่ระบบได้ เพราะ HMAC ใช้ `HASH_PEPPER`
  (ถ้าไม่ได้ตั้ง `HASH_PEPPER` จะใช้ `ENCRYPTION_KEY` แทน กรณีนั้นเปลี่ยนกุญแจแล้วจะเข้าสู่ระบบไม่ได้)
- ตาราง `app_user` และ `user_session` ไม่อยู่ในพจนานุกรมข้อมูลบทที่ 3
